## 1. 项目定位与约束

一个**单人**掼蛋（江苏规则）：你坐南家，另外三家由 AI 控制。

三条硬约束决定了整个技术选型：

| 约束 | 原因 | 结果 |
|---|---|---|
| **零运行时依赖** | 要能单文件双击打开、要在手机上离线跑 | 没有游戏框架、没有 UI 库、没有状态管理库；`package.json` 的 `dependencies` 是空的 |
| **核心逻辑必须可测** | 掼蛋规则细节极多（逢人配、接风、进贡、抗贡、过 A），靠手玩测不出来 | `src/core/` 完全不碰 DOM，可以在 Node 里跑几万局自对弈 |
| **可复现** | 出了问题要能精确重放 | 洗牌用 `mulberry32(seed)`，同一 seed 永远同一副牌；引擎支持快照 / 恢复 |

技术栈：**Vite + TypeScript(strict) + 原生 DOM/CSS + Vitest + jsdom**。
没有一个 UI 框架——因为界面本身不复杂，而掼蛋的复杂度全在规则和 AI 上。

## 2. 分层：纯逻辑内核 + 表现层

```
src/
├─ core/   纯逻辑：不 import 任何 DOM / 浏览器 API，可在 Node 里直接跑
└─ ui/     表现层：把 core 的状态画成界面，把用户操作翻译成 core 的方法调用
```

**依赖方向是单向的**：`ui → core`，`core` 永远不知道 `ui` 存在。这条规则带来三个好处：

1. **AI 自对弈可以在 Node 里跑**——`autoplay.ts` 不依赖浏览器，所以基准测试能连跑几百局。
2. **UI 换掉不影响规则**——如果哪天要换 React 或做桌面端，`core/` 一行不用改。
3. **测试分两档**——`core` 用纯 Node 测（快、确定），`ui` 用 jsdom 测（慢一点）。

## 4. 数据模型

```ts
type Card = { id: number; suit: 'S'|'H'|'D'|'C'|'J'; rank: number; deck: 0|1 }
//  rank: 2..14 = 2..A，15 = 小王，16 = 大王

type Combo = {
  type: ComboType      // Single/Pair/Triple/FullHouse/Straight/Tube/Plate/Bomb/StraightFlush/JokerBomb
  cards: Card[]
  rank: number         // 同类型内部比大小用
  power: number        // 压制力（普通牌型 0，炸弹 104 起）
  isBomb: boolean
  label: string        // 中文名，直接给界面用
  wildAs?: WildAs[]    // 逢人配被当成了什么（只在真正替代时才有）
}
```

两个设计决定值得注意：

**① `id` 是全局唯一的 0..107**。所有涉及"这几张牌"的地方都用 id 集合，不用对象引用。
这样拖拽重排、选中、快照恢复都不会出现引用错乱。

**② `rank` 和 `power` 分开**。`rank` 用于同类型比较（对 5 比对 3 大），`power` 用于跨类型比较
（炸弹永远压普通牌型）。掼蛋的压制序里同花顺卡在 5 张炸和 6 张炸之间，用 `power`
表达比用一堆 if 清楚得多：

```
普通牌型 power = 0
4 张炸 104 → 5 张炸 105 → 同花顺 105.5 → 6 张炸 106 → … → 10 张炸 110 → 四大天王 200
```

## 5. 规则即配置

掼蛋是地方规则差异极大的游戏。`RuleConfig` 把所有分歧点做成配置项（`DEFAULT_RULES` 是默认值）：

| 配置 | 默认 | 说明 |
|---|---|---|
| `levelStart` / `levelCap` | 2 / 14 | 从打 2 开始，过 A 结束 |
| `bombMaxSize` | 10 | 最多几张的炸弹 |
| `straightFlushBetween5And6` | true | 同花顺卡在 5 张炸与 6 张炸之间 |
| `allowAceLowInStraight` | true | A 可当 1（A2345） |
| `allowAceLowInTubePlate` | true | 连对/钢板里的 A 也可当 1 |
| `tributeEnabled` | true | 是否进贡 |
| `tributeReturnMaxRank` | 10 | 还贡的牌不得大于 10 |
| `doubleTributeBigToHead` | true | 双贡时大的那张给头游 |
| `passACondition` | `notLast` | 过 A 需要"一人头游 + 另一人非末游" |
| `aRetryLimit` / `aRetryPolicy` | 3 / `reset` | 三次打 A 不过就退回 2 |
| `endEarlyOnDoubleDown` | true | 双下（队友包揽头游二游）提前结束本局 |

**这个决定的价值**：规则分歧不会变成代码里的 if 分支，而是变成一组参数。
测试可以针对不同配置跑同一套逻辑，`docs/RULES.md` 里的每条规则也都能对应到一个开关。

## 6. 牌型识别：逢人配带来的组合爆炸

这是整个项目**最容易出错**的地方，值得单独讲。

**问题**：红桃级牌是"逢人配"，可以当除大小王外的任意牌。于是同一组牌可能有多种解释。
例如 `红桃7 红桃8 红桃2 红桃10 红桃J`（打 2）：

- 红桃2 当自己（点数 2）→ 点数是 7,8,2,10,11 → **不成牌型**
- 红桃2 当红桃9 → `7 8 9 10 J` 同花 → **同花顺**

**做法**：`detectCombos` 枚举逢人配的所有可能指派（点数 × 花色），对每种指派跑 `classify`，
把结果按 `comboKey`（类型+张数+点数+power）去重。

代价是指派空间很大，所以加了两道闸：

1. **花色只需考虑"场上已有的花色 + 黑桃 + 红桃"**——同花顺只可能出现在这些花色里。
2. **结果按 card-set 缓存**（`detectCache`），同一批牌只算一次。

**规则：一手多解时一律取最强解释**（`validatePlay` 返回 `pickStrongest(...)`）。
理由是这几张牌是同一批，强解释在压制上严格不劣于弱解释，玩家没有理由选弱的。

**踩过的坑**：最早 `validatePlay` 返回的是**最弱**解释，于是上面那手牌被判成"顺子"而不是"同花顺"，
被下家的炸弹压了——玩家一眼就看出不对。这个 bug 是玩家报上来的，修法是改用 `pickStrongest`。

**连带的坑**：`wildAs` 一开始是无条件挂上去的，导致"红桃2 当自己用"也会显示"含配"。
现在的规则是**只有真正发生替代才标记**（指派不等于它自己的身份），并且显示成"配当♦4"
让玩家可以自己核对。

## 7. 走法生成

`enumeratePlays(hand, level, target, rules)` 返回**所有合法出法**。`target` 为 `null` 时是首出。

流程：把手牌建成 `HandModel`（按点数分组 + 逢人配单独放），然后按牌型逐个生成：

```
单张 / 对子 / 三同张 / 三带二     按点数 + 逢人配补张
顺子                              5 张连续点数窗口
连对（三连对）                     3 个连续点数各 2 张
钢板                              2 个连续点数各 3 张
炸弹                              4..bombMaxSize 张同点
同花顺                            同花色的 5 张连续点数窗口
四大天王                           大小王各 2 张
```

生成后做两件事：

1. **过滤**：有 `target` 时只留能压过的（`beats`）。
2. **按牌去重**：同一组牌可能有多种牌型解释（例如既是顺子又是同花顺），
   保留 `pickStrongest` 的那个，避免 AI 把同一批牌当成两个选项来比。

## 8. 对局引擎：状态机 + 事件流

`GuandanGame` 是一个显式状态机：

```
roundEnd → startRound() → (returnTribute 还贡) → playing → endRound() → roundEnd
                                                                  ↘ matchEnd（有人过 A）
```

**出牌流程**：`play(player, cards)`
1. 校验：是不是轮到你、牌在不在手里、牌型合不合法、压不压得过
2. 扣手牌、更新 `lastPlay`、把记录推进 `history` 和 `trickPlays`
3. 推事件（`play` / `pass` / `trick` / `finish` / `roundEnd` …）

**事件流是 UI 的唯一驱动**：界面不主动轮询引擎，而是 `drainEvents()` 取事件，
按事件播动画、放音效、弹提示。这样"引擎发生了什么"和"界面演了什么"是同一条链。

**关键设计**：
- `history` 里每条记录带 `trick`（第几轮），因为界面需要按轮分组；它也让"复盘"能精确定位。
- `pass()` 也会写 `history`——否则复盘无法还原"谁在这一轮不要"。
- 支持 `snapshot()` / `fromSnapshot()`：AI 基准测试用它来快速重置，
  也让"双下提前结束"这类边界情况可复现。

## 9. AI

**不是大模型，是本地的规则 + 启发式评估。** 完整剖析见 [`AI.md`](AI.md)，这里只放一句话版：

```
枚举所有合法出法 → 每种子模拟"出完之后我的手牌"→ 用估值函数打分 → 选分最低的
```

难度差异来自**参数表**（是否记牌、是否算炸弹威胁、惩罚权重、随机化比例），
详见 [`AI.md` 第 6 节](AI.md#6-难度是怎么区分的)。

## 10. 表现层

**渲染策略**：`renderApp` 一次性重建 DOM。听起来很暴力，但 27 张牌 × 4 家的规模下完全够快，
而且**没有状态同步 bug**——不用维护"哪个 DOM 对应哪个状态"。

只有一处例外：**点牌选中不重建**。早期每次点牌都重建 DOM，导致 `dblclick` 的目标节点
在两次点击之间被换掉，双击选同点数完全失效。修法是 `renderPartial` + `updateSelectionClasses`
——只改 class，不动结构。

**动画**：`anim.ts` 用 FLIP（First-Last-Invert-Play）做手牌重排的位移动画，
出牌用飞行元素从座位飞到牌桌中央。都是纯 CSS transition + `requestAnimationFrame`。

**音效**：`sound.ts` 全部用 Web Audio 实时合成（多个分音叠加 + 包络），
**不含任何音频文件**——单文件版因此才能只有一个 html。

**理牌**：`handOrganizer.ts` 把 27 张拆成"顺子 / 三带二 / 炸弹 / 对子 / 散张 / 逢人配"等区块，
玩家可以自由拖拽重排、成组、拆组、改名。分组是**视图层状态**，引擎不关心。

## 11. 测试策略

**157 个测试，12 个文件**，分四档：

| 档位 | 文件 | 测什么 |
|---|---|---|
| **规则正确性** | `combos`(20) `interpretation`(13) `candidates`(12) | 牌型判定、逢人配多解、走法生成 |
| **引擎行为** | `engine`(29) | 完整对局、进贡抗贡、升级结算、轮次标记、快照 |
| **AI** | `ai`(18) `aiThreat`(7) `aiBombLadder`(4) | 跟牌必过牌或出合法牌、威胁反应、炸弹阶梯 |
| **UI** | `ui`(29) `uiAnim`(8) `handOrganizer`(13) `sound`(3) | jsdom 里真实点击：选牌、拖拽、弹层、快捷键 |
| **基准** | `aiBench`(1) | 自对弈 300+ 局，统计胜率与决策耗时 |

两个贯穿全项目的测试习惯：

1. **竞态测试**：`ai.test.ts` 里跑"AI vs AI 连打多场"，断言**无非法动作、无死锁**。
   规则改动最容易在这里翻车。
2. **回归测试要带现场**：玩家的每个 bug 报告都先写一个**能复现的最小局面**，再修。
   例如"有 4 张 K 炸却烧了同花顺"，就是构造一个座位 3 面对钢板、手里同时有两种炸的局面。

## 12. 构建与分发

| 命令 | 产物 | 用途 |
|---|---|---|
| `npm run dev` | 开发服务器 | 改代码即时热更新 |
| `npm run build` | `dist/` | 标准静态站 + PWA（可安装、可离线） |
| `npm run build:single` | `release/掼蛋.html` | **单个 html，双击就玩**（122 KB，全部内联） |
| `npm run share` | 局域网 URL + 二维码 | 手机扫码玩 |
| `npm run test` / `bench` / `e2e` | — | 测试 / 基准 / 真实浏览器 E2E |

**PWA** 用 `vite-plugin-pwa`，离线靠 Service Worker 预缓存 13 项资源。
有一个专门处理的问题：**改了代码但页面还是旧版**——`autoUpdate` 只在后台下载新版本，
不刷新界面。现在加了 `controllerchange` 监听（带首次安装守卫）来自动 reload。

**单文件版**用 `vite-plugin-singlefile` 把 JS/CSS/图标全部内联。
代价是不能注册 Service Worker（`file://` 下浏览器不允许），但它本来就是本地文件，天然离线。

**CI**：推送到 `main` 自动跑 `npm ci → npm test → npm run build` → 发布 GitHub Pages。
踩过一个坑：CI 第一次跑挂在 `node-version: 20`——**jsdom 30 依赖的 undici 需要更新的 Node**，
两个 jsdom 测试文件在加载阶段就崩了，表现为"106 个测试全过但退出码 1"。改成 Node 24 解决。

## 13. 这个项目踩过的坑

留给后来者，每条都是真实发生过的：

| 坑 | 症状 | 根因与修法 |
|---|---|---|
| **一手多解取了最弱解释** | 红桃 7 8 (配) 10 J 被判成顺子，被炸弹压 | `validatePlay` 改用 `pickStrongest` |
| **逢人配标记含糊** | "没用到逢人配却显示含配" | 只在真正替代时标记，显示改成"配当♦4" |
| **炸弹阶梯反了** | 有 4 张 K 炸却烧同花顺 | "只有炸弹能压"的场面让同花顺免罚了；引入随压制力单调递增的 `bombCost` |
| **同花顺被当成炸弹捂着** | hard 档胜率从 53.8% 掉到 44.3% | 同花顺同时是顺子，不该按炸弹计价；改为只在"有更便宜的压法"时计代价 |
| **点牌选中后双击失效** | 双击选同点数不工作 | 每次点牌都重建 DOM，`dblclick` 目标被换掉；改 `renderPartial` |
| **重命名输入框失焦** | 输入框刚点开就关闭 | `mousedown` 抢焦点；改由 ✎ 按钮触发 + 一帧守卫 |
| **回放访问 `hands[-1]`** | 观战模式崩溃 | 观战是 `human = -1`，加了 `humanIndex` 守卫 |
| **绝对定位浮层被挤窄** | 4 张牌折行 | 收缩宽度按"标记本身"算；加 `width: max-content` |
| **CI 环境差异** | 测试全过但退出码 1 | Node 20 上 jsdom 30 崩；升到 Node 24 |
| **PWA 缓存旧版** | 改动已发布但页面没变 | 加 `controllerchange` 自动 reload |

**最值得记住的一条**：这个项目的多数真实 bug **不是测试发现的，是玩家玩出来的**。
自对弈基准能测出"变弱了"，但测不出"这手牌不像人打的"——
所以每一条玩家反馈都值得先复现、再修、再补回归测试（见 [`AI.md` 第 9 节](AI.md#9-改进方案)）。
